# Исправления в библиотеке audioI2S / Fixes applied to the audioI2S library

Файл-память: что именно и почему было изменено в этой аудио-библиотеке по сравнению
с исходным кодом, который был взят из upstream (`ESP32-audioI2S`). Нужен, чтобы при
следующем обновлении библиотеки правки не потерялись и не были «починены обратно».

> **Important for anyone updating this library from upstream:** every defect listed
> here is also present in the pinned upstream decoder and in the Maleksm fork. They
> are **not** regressions of this fork, and pulling a newer upstream will **not** fix
> them — in one case (E-VS-A) upstream is actually worse. Re-apply these patches.

# Часть 1. Транспорт webstream (коммит `7691b62`)

## E-AT1 — соединение переиспользовалось по одному только hostname

**Было.** `httpPrint()` решал, можно ли оставить открытый сокет, по сравнению
`hwoe.equals(cur_hwoe)` — то есть только по имени хоста.

Последствия:

* тот же хост на **другом порту** → сокет не закрывался, запрос уходил на старый порт;
* **`http → https`** на одном хосте → `m_f_ssl` уже переключён строкой выше, но
  `m_client` всё ещё указывал на обычный `client`; так как он «подключён», весь блок
  переподключения пропускался и **TLS-запрос уходил открытым текстом**;
* **`https → http`** — зеркально, обычный запрос уходил в TLS-клиент.

**Стало.** Идентичность endpoint = `hostname + схема + эффективный порт`, причём
старый endpoint читается из **предыдущего URL до** перезаписи текущих полей
(`audio_safe::sameHttpEndpoint` в `audio_text_url_utils.h`).

Байтовое сравнение hostname оставлено как было — без case folding, IDN и нормализации
завершающей точки, чтобы не расширять поведение.

## E-AT2 — ошибка разбора URL не доезжала до вызывающего

**Было.** `parseUrl()` корректно отвергал битый URL, но `dismantle_host()` возвращал
структуру без признака ошибки. Вызывающие продолжали работу с пустыми полями:

* `connecttohost()` доходил до `setDefaults()` и DNS-запроса пустой строки, а результат
  подавался как обычный сетевой отказ (`CONN_LOST` в mem-watchdog);
* `httpPrint()` успевал **закрыть живой сокет** до того, как выяснялось, что URL негоден.

**Стало.** `audiolib::hwoe_t` получил поле `valid`, и `connecttohost()` / `httpPrint()` /
`httpRange()` выходят с ошибкой **до** любых действий с транспортом, cleanup и отправки
запроса. Некорректный URL больше не путается с временным сетевым отказом.

Поддерживаемые формы URL, а также обработка signed/query/`%xx` — не менялись.

## E-AT3 — TLS не получал имя хоста

**Было.** Проект резолвит DNS сам (`networkResolveHostForConnect`), после чего вызывался
`connect(IPAddress, port)`. В ядре Arduino-ESP32 этот overload передаёт `host = NULL` в
`start_ssl_client()`, а `mbedtls_ssl_set_hostname()` подставляет `ip.toString()` — то есть
в SNI уходил **IP-литерал вместо имени станции**.

**Стало.** Собственный resolver сохранён, но для TLS используется единственный публичный
API ядра, принимающий готовый IP вместе с именем хоста:

```cpp
int NetworkClientSecure::connect(IPAddress ip, uint16_t port, const char *host,
                                 const char *CA_cert, const char *cert,
                                 const char *private_key);   // core 3.3.11
```

Вызов идёт через тонкую обёртку `AudioTlsSniClientT` (`audio_tls_sni_client.h`), которая
как наследник передаёт **те же самые** credentials, что использовал бы базовый
`connect(ip, port)`. Поэтому `setInsecure()`, CA-bundle, ALPN и таймауты не меняются —
добавляется только имя хоста. Режим PSK оставлен на стоковом пути, обычный HTTP
по-прежнему идёт через `connect(ip, port)`, а URL с буквальным IP ведёт себя как раньше
(имя хоста тогда и есть строка IP).

Private-поля TLS не трогались, новый API не изобретался.

## E-AT4 — один бюджет на две попытки подключения

**Было.** `pollWebstreamReconnect()` списывал **одну** единицу бюджета через
`attemptInternalReconnect(true)`, но дальше мог выполнить **две** физические попытки:
buffered-переподключение через `httpPrint()`, а при его неудаче — clean fallback через
`connecttohost()`. При `MAX_UNSTABLE_STREAM_FAILURES = 6` это давало до **12** реальных
подключений на один бюджет.

**Стало.** Обе точки списания проходят через общий helper
`audio_safe::retryBudgetTryConsume` (`audio_retry_budget.h`).
`tryBufferedWebstreamReconnect()` сообщает, была ли реально открыта сокет-попытка (все
его ранние отказы не стоят ничего), и clean fallback берёт **собственную** единицу либо
уходит в штатный terminal stop.

**Правило: одна физическая попытка подключения = одна единица бюджета, потолок 6.**

Сброс бюджета остался за прежними владельцами и не менялся:

* `pollStreamStability()` — поток доказал стабильность (15 с непрерывного PCM);
* `beginPlaybackSession()` — смена станции / ручной PLAY;
* `finishUnstableStreamExhausted()` — бюджет исчерпан, terminal stop.

Второй механизм retry не вводился. Session guard, terminal-stop contract и приоритет
ручного STOP не менялись. Прерывание синхронного TLS-connect посередине вызова не
обещается и не реализовано.

# Часть 2. Декодер Ogg/Vorbis (коммит `db188ec`)

## Авария, с которой всё началось

Прошивка `fu4.2.15`, станция `http://89.223.45.5:8000/geny-160` (ogg-vorbis), после
штатного пробуждения по таймеру:

```
##AUDIO.INFO#: syncword found at pos 2787
##AUDIO.INFO#: syncword found at pos 0
Guru Meditation Error: Core 1 panic'ed (LoadProhibited)
PC : 0x4209ff34   A2 : 0x00000000   EXCVADDR: 0x00000000
#0 mapping_inverse   #1 vorbis_dsp_synthesis   #2 vorbisDecodePage4
#3 VORBISDecode      #4 Audio::sendBytes
```

Разбор: по адресу `PC` стоит `l32i.n a8, a2, 0`, то есть чтение `info->submaps` —
первого поля структуры. `a2` — это аргумент `info`, и он равен нулю. Отсюда
`EXCVADDR = 0`.

Цепочка целиком:

1. resync на подтормаживающем потоке увёл парсер в разбор setup-заголовка по
   невыровненным данным;
2. `bitReader()` за концом пакета вернул `-1`, `s_nrOfMaps` стал `0`;
3. `s_map_param.alloc(0)` вернул **NULL** — и сообщить об этом было некому,
   `ps_ptr::alloc()` возвращает `void`;
4. проверка `mapping >= s_nrOfMaps` честно отработала и ушла в `err_out`;
5. **но `vorbisDecodePage3()` выбросил результат** и всё равно выставил `s_pageNr = 4`
   и создал dsp-state;
6. следующий аудиопакет → `mapping_inverse(nullptr)` → паника.

Ошибок в логе не было видно, потому что `CORE_DEBUG_LEVEL = 0` полностью глушит
`VORBIS_LOG_ERROR` (см. «Намеренно не менялось»).

## E-VS1 — счётчики setup-заголовка

`parseVorbisCodebook()` читает пять счётчиков как «значение + 1» и сразу использует их
размером выделения. На конце пакета `bitReader()` возвращает `-1`, счётчик тихо
становится нулём, а `alloc(0)` отдаёт NULL.

Теперь конец пакета отвергается прямо в месте чтения — пока это ещё обычная ошибка
заголовка. Защищены все пять: codebooks, floors, residues, mappings, modes.

Отвергается **только** случай `-1`. Диапазон значений и прежнее поведение при
переполнении сознательно не трогались (см. «Намеренно не менялось»).

## E-VS2 — page 3 игнорировал результат разбора

`vorbisDecodePage3()` безусловно выполнял `s_pageNr = 4; s_dsp_state = vorbis_dsp_create();`
даже когда `parseVorbisCodebook()` вернул ошибку.

Теперь аудио-декодирование включается только при успешном разборе. При ошибке —
`s_pageNr = 0`, то есть ожидание новой полной цепочки заголовков.

**Важная тонкость:** просто «не ставить 4» небезопасно. Проба `"vorbis"` в начале
`VORBISDecode()` поднимает любое значение меньше 4 на единицу, поэтому при `s_pageNr == 3`
следующий же сегмент попал бы на page 4 вообще без кодбуков — та же авария. Из `0`
вернуться на page 4 можно только пройдя page 1 → 2 → 3, а `vorbisDecodePage1()` по дороге
вызывает `clearGlobalConfigurations()` и корректно освобождает недостроенные таблицы.

Учёт байтов (`*bytesLeft`, `s_vorbisCurrentFilePos`) намеренно вынесен из ветвления:
поток продвигается в обоих случаях, поэтому зациклиться на одних и тех же байтах нельзя.

## E-VS4 — resync не выравнивал парсер Ogg

Самая маленькая и самая ценная правка: она устраняет не последствие, а причину.

При потере синхронизации `findNextSync()` сбрасывал состояние **только MP3**
(`MP3Decoder_ClearBuffer()`). У Vorbis такого сброса не было, поэтому после resync в
парсере оставалась устаревшая таблица сегментов Ogg: заголовок следующей страницы
читался как аудио, и парсер мог уйти в разбор заголовков по мусору.

Теперь для Vorbis вызывается `VORBISDecoder_ClearBuffers()`, который дополнительно
сбрасывает `s_lastSegmentTableLen`, `s_f_parseOggDone` и `s_f_oggContinuedPage` — без них
выравнивание было бы половинчатым.

**Кодбуки и `s_pageNr` при этом намеренно сохраняются** — именно поэтому звук
продолжается со следующей же аудиостраницы, **без разрыва**.

## E-VS3 — быстрое восстановление вместо тишины

Если setup-заголовок всё-таки непригоден, ждать в состоянии `s_pageNr = 0` плохо:
кодбуки Vorbis приходят только в начале логического потока, а следующая цепочка
заголовков у Icecast может прийти лишь на смене трека — то есть минуты тишины.

Теперь декодер взводит одноразовый флаг (`VORBISConsumeSetupHeaderFailure()`), а
`Audio::sendBytes()` закрывает сокет и передаёт восстановление **существующему**
механизму переподключения webstream. Сервер всегда отдаёт цепочку заголовков при
подключении, поэтому звук возвращается примерно за `WEBSTREAM_RECONNECT_GRACE_MS` (250 мс)
плюс время connect — то есть за доли секунды.

Второй механизм retry не вводился: используется тот же бюджет, тот же session guard, тот
же приоритет ручного STOP и тот же terminal-stop contract. Если станция действительно
битая — 6 попыток и штатная остановка.

В логе это видно строкой (идёт через `Serial.printf`, а не через заглушённый канал
декодера):

```
[AUDIO.RETRY] vorbis setup header unusable -> reopen stream session=N
```

## E-VS5 — обе записи в буфер отложенного пакета

`vorbisDecodePage4()` сохраняет последний сегмент страницы Ogg, чтобы склеить его с
продолжением на следующей. Буфер выделялся литералом 4096, а заполнялся из двух мест
с несогласованными границами: continued-путь проверял против литерала **1024**, обычный
путь — **не проверял вообще**.

Одна запись Ogg lacing суммирует серии по 255, поэтому `segmentLength` законно доходит
до 255×255 = 65025. Пакет больше буфера — а его даёт и высокий битрейт, и битая
lacing-таблица после ложного `OggS` — затирал кучу. Такая порча не падает там, где
случилась: она всплывает позже и в другом месте, ровно как авария fu4.2.15.

Теперь оба места используют одну именованную ёмкость `VORBIS_LAST_SEGMENT_CAPACITY`,
поднятую до 16 КиБ (худший реальный пакет Vorbis — около 12 КиБ). При превышении
страница отвергается, вызывающий делает resync: цена — один пакет, а не куча.

> Обе правки только **расширяют** принимаемое: прежнее переполнение было неопределённым
> поведением, а лимит 1024 отвергал пакеты, которые буфер и так вмещал.

## E-VS6 — ошибки декодера были немыми

`VORBIS_LOG_ERROR` гасился условием `CORE_DEBUG_LEVEL >= 1` **внутри** тела функции,
а проект собирается с `-DCORE_DEBUG_LEVEL=0`. Компилятор такое не выбрасывает: каждая
ошибка форматировалась (два выделения `ps_ptr`, четыре прохода `snprintf`) и
выбрасывалась. Работа оплачивалась, вывода не было — и именно его не хватало при
разборе аварии.

Уровень ERROR больше не смотрит на `CORE_DEBUG_LEVEL`. Остальные уровни под прежним
гейтом, `log_e` ядра по-прежнему выключен — шума от WiFi/TLS/lwIP нет. Рантайм-
переключатель `audioinfo` продолжает управлять выводом.

⚠️ Известный источник шума: `VORBISFindSyncWord()` пишет при каждом неудачном поиске
синхры и на разваливающемся потоке может лить часто.

## E-VS7 — переоткрытие Vorbis выполнялось из чужой задачи

Запрос на переоткрытие (E-VS3) звал `m_client->stop()` и `scheduleWebstreamReconnect()`
прямо из `sendBytes()`. Но `sendBytes()` идёт по цепочке
`taskWrapper → audioTask → performAudioTask → playAudioData`, то есть в **отдельной
задаче**, а сокет читает и пишет `Audio::loop()` из `Player::loop()` — другая задача.
Общего мьютекса на этом пути нет: `mutex_playAudioData` берут только точки подключения.

Теперь аудиозадача публикует только запрос и свою `playback session`, а
`pollVorbisReopenRequest()` — первым делом в `Audio::loop()` — закрывает сокет и
планирует переподключение. Запрос с несовпадающей сессией отбрасывается, поэтому ручной
STOP и смена станции сохраняют приоритет. Сетевых вызовов в аудиозадаче не появилось.

# Часть 3. Восстановление MP3 webstream (коммит `7595921`)

## E-MP1 — TLS cleanup освобождал работающий декодер

`tlsPreconnectCleanup()` безусловно звал `MP3Decoder_FreeBuffers()`. Пока это
выполняется в задаче Player, аудиозадача продолжает декодировать удержанный буфер —
то есть use-after-free. Функция теперь принимает кодек, чей декодер обязан пережить
cleanup.

## E-MP2 — MP3 терял буфер при каждом переподключении

`connecttohost()` через `setDefaults()` сбрасывает `InBuff`, поэтому при каждом обрыве
выбрасывалось около восьми секунд уже скачанного звука — слышно как пауза каждые ~20 с
на станции, которая столько и живёт. Путь, который этого избегает, существовал, но был
заперт на AAC.

## E-MP3 — удержанный буфер рос без предела

Первая попытка (просто дописывать новый поток за старым, без дедупликации) дала рост
**+80 КиБ за цикл**: 126 КиБ → 629 КиБ за семь переподключений, около 39 с отставания
от эфира и путь к потолку буфера. На слух — повторы фрагментов. Причина: Icecast при
переподключении переотдаёт burst из своего буфера.

Остался вторичный предохранитель `MP3_BUFFERED_RETAIN_DIVISOR`: выше порога идёт обычный
clean reconnect, сбрасывающий и буфер, и отставание. После E-MP4 срабатывать он почти не
должен.

## E-MP4 — дедупликация была без нужды заперта на AAC

Ключевое наблюдение: **матчер побайтовый и о кодеках ничего не знает.** Он ищет точную
сигнатуру в 1024 байта сырого payload — уже после снятия ICY и chunk-обрамления. Поэтому
второй dedup писать не потребовалось: сняты шесть гейтов по кодеку через один
`overlapDedupEligibleCodec()` — кольцевой хвост, заморозка сигнатуры, старт матчера,
сторож зависания PCM, его арминг и фолбэк.

Staging (192 КиБ PSRAM) и лимиты поиска (192 КиБ / 10 с) **переиспользуются**, а не
дублируются: второго буфера не появляется. Но «переиспользуется» не значит «бесплатно»:
буфер выделяется лениво, при первом переподключении, которое до него дошло. На чисто
MP3-станции это выделение теперь может случиться **впервые именно на MP3** — в логе это
видно как `[AUDIO.DEDUP] PSRAM staging ready bytes=196608`. Пик потребления PSRAM не
вырос, но момент его появления сместился.

Настоящей новой логики потребовало одно место — фолбэк
`restartAacAfterBufferedReconnect()` звал `AACDecoder_FreeBuffers/AllocateBuffers` и
`m_frameSizeAAC` напрямую. Теперь диспетчеризуется по кодеку; ветка AAC байт в байт
прежняя.

**Данные с устройства** (chantefrance, MP3 через https-редирект): три переподключения
подряд, совпадение точное — отброшено 84010 / 91533 / 82756 байт, перекрытие 5,2–5,7 с,
`kept=0`, после каждого `PCM verified`, буфер стабилен на ~125 КиБ.

⚠️ Бесшовность не гарантируется: если старый буфер кончится раньше, чем поднимется
соединение, пауза допустима.

⚠️ Две оговорки о том, чего дедуп **не** доказывает, и обе сохраняются:
* **Первое совпадение сигнатуры не доказывает её уникальность.** 1024 байта подобраны
  так, чтобы случайное совпадение было крайне маловероятным, но матчер останавливается
  на первом найденном, а не проверяет, что оно единственное на всём просканированном
  окне.
* **`PCM verified` не отслеживает фактический переход границы.** Он говорит только, что
  декодер продолжил выдавать сэмплы после переподключения, — а не что воспроизведение
  дошло до стыка старых и новых данных и прошло его без разрыва.

# Часть 4. FLAC и контейнер Ogg

## E-FL1 — разрядность читалась со сдвигом на бит

В STREAMINFO разрядность записана пятью битами как `bps - 1`: старший бит — бит 0 байта 12,
младшие четыре — верхний ниббл байта 13. В коде стоял сдвиг на **5** вместо **4**, поэтому
старший бит давал 32 вместо 16.

24-битный поток (`bps - 1 = 23 = 0b10111`) превращался в `32 + 8 = 40`, и в логе появлялось
`Flac, bits per sample > 16, bps: 40`.

**Почему это жило годами:** на 16-битных потоках `bps - 1 = 15`, старший бит нулевой, и
ошибочный сдвиг умножается на ноль. Баг проявляется только при `bps >= 17` — то есть ровно
там, где декодер всё равно отказывает по ограничению `> 16`.

⚠️ Исправление делает диагностику честной (`bps: 24` вместо `40`), но **не добавляет
поддержку 24 бит** — ограничение на выходе осталось. Реализация 24-бит есть у Maleksm и в
свежем upstream; это отдельная задача.

## E-FL2 — стартовый запас для потоков в Ogg

У AAC prebuffer был (32 КиБ), у потоков в контейнере Ogg — нет.

**Ключевая тонкость:** в точке проверки порога станция ещё `CODEC_OGG` — настоящий кодек
определяется только внутри ветки ниже. Проверка на `CODEC_FLAC` не сработала бы никогда.
В логе это видно как `format is ogg` -> `format is flac` -> `stream ready`.

Одна константа тут не работает: между Vorbis 160 кбит/с и FLAC 1,4 Мбит/с почти
десятикратный разброс. Поэтому запас считается **во времени** (около 0,5 с) от заявленного
`icy-bitrate`, с границами 16...96 КиБ. Порог только поднимается (`max`), поэтому там, где
расчёт ниже существующего `maxFrameSize`, не меняется ничего.

Отдельное умолчание — 64 КиБ — для станций, которые `icy-bitrate` не сообщают: нижняя
граница дала бы им символические 0,13 с при ~1 Мбит/с, а все встреченные Ogg-станции без
объявленного битрейта оказались высокобитрейтным FLAC.

**Данные с устройства:** Radio Paradise 1441 кбит/с получил 90 КиБ и за прогон не выдал ни
одного `slow stream`, хотя раньше выдавал. Vorbis 160 кбит/с получил нижнюю границу, старт
замедлился примерно на 0,3 с.

⚠️ Prebuffer задаёт глубину **на старте**. При устойчивой нехватке канала он отодвигает
провалы, но не убирает их.

# Часть 5. Владение остановкой воспроизведения

## E-ST1 — аудиозадача вызывала `stopSong()` напрямую

`stopSong()` по своему устройству **межзадачный**: он поднимает `m_f_lockInBuffer`, затем
крутится в `while(m_f_audioTaskIsDecoding)`, дожидаясь, пока аудиозадача выйдет из декодера,
и только потом освобождает буферы декодера и закрывает `m_client`. Это рукопожатие
«владелец ждёт исполнителя», и оно корректно ровно до тех пор, пока зовёт его **не сама**
аудиозадача.

Четыре точки звали его именно оттуда:

| Точка | Условие |
|---|---|
| `decodeError()` | `res == -100` (для FLAC это `FLAC_STOP`) |
| `setDecoderItems()` | `bitsPerSample` не 8 и не 16 |
| `setDecoderItems()` | число каналов не 1 и не 2 |
| `sendBytes()` | ветка `default:` — кодек не распознан |

Все четыре достижимы только по цепочке `audioTask -> performAudioTask -> playAudioData ->
sendBytes`, то есть всегда из аудиозадачи. Последствий три, и все три реальные:

1. **Ожидание самого себя.** `playAudioData()` выставляет `m_f_audioTaskIsDecoding = true`
   на входе и сбрасывает только на выходе через `exit:`. Вызванный изнутри, `stopSong()`
   ждёт флаг, который держит его же собственный кадр стека, и выходит только по
   таймауту (~100 мс).
2. **Освобождение декодера из самого декодера.** После таймаута `stopSong()` спокойно
   освобождает буферы кодека, хотя ниже по стеку в них ещё находится `FLACDecode()` или
   `VORBISDecode()`. Это тот же класс дефекта, что E-MP1 и E-VS7, только с другой стороны.
3. **Закрытие сокета из-под читателя.** `m_client` принадлежит задаче Player, и она в этот
   момент может быть внутри `m_client->read()`.

**Правка** повторяет паттерн E-VS7: аудиозадача больше не выполняет остановку, а публикует
запрос — причину плюс `m_playbackSession`, — и гасит `m_f_playing`, чтобы оставшиеся
миллисекунды не ушли на разбор заведомо негодных данных. `Audio::loop()` первой же строкой,
до всех ранних `return`, забирает запрос и выполняет `stopSong()` уже из задачи-владельца.

**Session guard обязателен.** Запрос от playback session, которую успели сменить, молча
отбрасывается: иначе отложенная остановка мёртвого потока убила бы станцию, которую
пользователь уже включил вручную. Ручной STOP и смена станции сохраняют приоритет.

Полнота набора проверена по графу вызовов, а не на глаз: остальные шесть `stopSong()` в
парсерах заголовков (`readAudioHeader`, `read_WAV_Header`, `read_FLAC_Header`,
`read_M4A_Header`) достижимы только через `processLocalFile()` / `processWebFile()`, а те
вызываются из `Audio::loop()`, то есть из задачи Player. `playAudioData()` не вызывает
ничего, кроме `playChunk()` и `sendBytes()`.

В серийнике появляются три строки: `[AUDIO.STOP] requested by audio task`,
`[AUDIO.STOP] executing` и `[AUDIO.STOP] dropped (stale)`. Последняя — **штатный** случай,
а не ошибка.

⚠️ Правка страхует путь, а не чинит наблюдаемый симптом: в проверочном прогоне фатальных
ошибок декодера не случилось, и ни одной строки `[AUDIO.STOP]` в логе нет. Поведение
исправных станций не меняется по построению.

## E-FL3 — prebuffer мог ждать порог вечно

E-FL2 поднял стартовый порог для потоков в Ogg до 16...96 КиБ, но **срока у ожидания не
было**: если поток столько байт не набирал, `m_f_stream` никогда не становился `true`,
декодер не запускался, и станция молчала бесконечно, оставаясь в UI в состоянии PLAYING.

Найдено на `dancewave.online` (Ogg FLAC, ~1,1 Мбит/с): сервер отдавал устройству около
30 КБ и замолкал, не закрывая сокет. Порог 65 536 не достигался, и станция молчала более
20 секунд при живом соединении.

**До E-FL2** порог был `maxFrameSize` (1600 байт), станция стартовала, проигрывала эти
30 КБ и уходила в reconnect. То есть E-FL2 превратил «играет пару секунд и срывается» в
«молчит навсегда» — строго худший исход.

**Правка:** если порог выше `maxFrameSize` не взят за
`STREAM_START_PREBUFFER_DEADLINE_MS` (5 с), он **опускается обратно к `maxFrameSize`**.
Порог только понижается и только до того значения, которое было в библиотеке до всех
prebuffer'ов, поэтому худший случай правки — стоковое поведение, а не новый неизвестный
режим. Срок применён к общему `streamStartThreshold`, а не отдельно к Ogg: AAC-prebuffer
(32 КиБ) живёт в коде дольше и имеет ровно ту же ловушку, просто на неё пока не наступила
ни одна станция.

Строка `[AUDIO.BUFFER] prebuffer deadline after ... -> start at ...` печатается только при
срабатывании, то есть в состоянии, которого на здоровой станции не бывает.

⚠️ E-FL3 убирает худший исход, но станцию не спасает: 27 КБ это ~0,2 с звука FLAC,
декодер не успевает выдать ни одного сэмпла, и поток всё равно уходит в reconnect.

# Часть 6. Передача управления при восстановлении

## E-HO1 — запрос между задачами передавался по частям

E-VS7 и E-ST1 ввели правильный принцип — аудиозадача публикует запрос, владелец его
исполняет, — но сама передача была собрана из `volatile bool` и отдельных обычных полей.
Три независимых дефекта:

**Запрос читался наполовину.** `poll` снимал флаг **до** чтения session и reason:

```
poll: flag = false;                     <-- окно открылось
      audio task: reason=X, session=Y, flag=true
poll: session = ...; reason = ...;      <-- читает новые
poll: session = 0;   reason = nullptr;  <-- затирает их
```

Новый запрос оставался с поднятым флагом, но с обнулённым содержимым, и на следующем
`poll` отбрасывался как устаревший. Настоящая фатальная ошибка декодера молча терялась.
Плюс к этому: `volatile` был только на флаге, поэтому порядок публикации остальных полей
компилятор мог переставить.

**Сессия бралась не у того потока.** `Player::_play()` вызывает `beginPlaybackSession()`
**до** того, как старый поток снесён: между инкрементом и `setDefaults()` внутри
`connecttohost()` аудиозадача продолжает декодировать **старый** поток, а
`m_playbackSession` уже содержит **новое** значение. Ошибка уходящего потока получала
идентификатор новой станции, проходила session guard и останавливала станцию, которую
пользователь только что выбрал.

**После terminal STOP декодирование продолжалось.** `m_f_playing = false` — не остановка:
`sendBytes()` читает его как «потеряна синхронизация», делает `findNextSync()`, снова
ставит `m_f_playing = true` и продолжает декодировать и публиковать PCM.

**Правка.**

* Запрос — POD (`pending` / `epoch` / `reason`), публикуется и забирается **целиком**
  под коротким `portMUX` spinlock. Внутри секции только копирование POD: ни сети, ни
  cleanup, ни ожиданий. `stopSong()` вызывается после выхода из секции.
* Введена **decode epoch** — идентификатор потока, который реально декодирует
  аудиозадача. Инкремент в `setDefaults()`, то есть там, где декодеры освобождены и
  `InBuff` сброшен, а **не** в `beginPlaybackSession()`, где новая станция лишь намечена.
  Buffered reconnect через `setDefaults()` намеренно не проходит, поэтому продолженный
  поток сохраняет epoch, и его запросы остаются в силе.
* Введён затвор `m_f_audioTaskStopGate`, который проверяют `performAudioTask()`,
  `playAudioData()` и `sendBytes()`. Только он реально удерживает аудиозадачу; уже
  декодированный PCM сбрасывается, а не доигрывается.

Сохранены: приоритет ручного STOP и смены станции, отбрасывание устаревших запросов
(с прежней строкой `[AUDIO.STOP] dropped (stale)`, теперь по epoch), единственный
terminal STOP (`if(!m_stopRequest.pending)`), общий retry-бюджет.

## E-HO2 — ответ нового соединения менял живой кодек до проверки

При buffered reconnect старый буфер продолжает играть, пока поднимается новое соединение.
Ответ разбирался прямо в живые поля:

1. `parseContentType()` писал новый кодек в `m_codec` — то самое поле, по которому
   `sendBytes()` выбирает декодер;
2. `initializeDecoder()` отрабатывал следом и для FLAC/OPUS/VORBIS **безусловно** звал
   `*_AllocateBuffers()` и `InBuff.changeMaxBlockSize()`;
3. и только **после** этого сравнивался кодек с сохранённым.

То есть станция, отдавшая при переподключении другой content-type, переключала работающий
декодер на удержанных байтах чужого формата и меняла буферы под ним прямо во время
декодирования.

**Правка.** Пока `m_f_preserveStreamReconnect` поднят, ответ разбирается в staging
(`m_stagedCodec` / `m_f_stagedOgg` / `m_stagedPlaylistFormat`) — тот же парсер, вынесенный
в `parseContentTypeInto()` с полями-параметрами; старое имя осталось тонкой обёрткой, и
обычный путь не изменился ни на байт. Совместимость проверяется до касания живых полей,
и при успехе `initializeDecoder()` **не вызывается вовсе**: декодер сохранённого кодека
уже выделен и работает, а повторная инициализация освободила бы буферы, которыми
пользуется аудиозадача.

Все три способа провалиться — плохой заголовок, несовместимый ответ, неудавшийся
redirect — сведены в один `finishPreserveReconnectFallback()`. Redirect раньше не
проверял результат `httpPrint()`, который при preserve возвращает `false` вместо вызова
`stopSong()`, и конечный автомат оставался ждать соединение, которое не открывалось.

Audio mutex на этом пути не удерживается: `httpPrint()` его не берёт, и DNS/socket/TLS
и ожидание заголовка проходят без него.

> `m_metaint` и `m_audioFileSize` заголовок по-прежнему пишет живьём. Аудиозадача их не
> читает, пока `m_streamType == ST_WEBSTREAM`, а совместимым считается только ответ с
> этим типом потока.

# Часть 7. Плейлист HLS

## E-HL1 — пауза между выборками включалась ровно один раз

В ветке m3u8 `Audio::loop()` при пустой выборке плейлиста счётчик
`m_lVar.no_host_cnt` увеличивается, а пауза ставилась так:

```cpp
if(m_lVar.no_host_cnt == 2){m_lVar.no_host_timer = millis() + 2000;}
```

Сравнение **на равенство**. Счётчик только растёт, поэтому пауза срабатывала ровно один
раз — на второй пустой выборке, — а все последующие шли вообще без паузы.

Станция, у которой плейлист перестал публиковать новые сегменты, начинала долбить CDN
вплотную. Замерено на `bss2.neterra.tv` (Витоша Club Classics): **~80 полных запросов
плейлиста по TLS за 54 секунды**, то есть 675 мс на запрос. Это отъедает CPU у аудиопути
и хорошо зарабатывает rate limit — то есть может продлевать то самое состояние, из
которого устройство пытается выйти.

**Правка** — три места одного механизма:

* `>= 2` вместо `== 2`;
* счётчик ограничен сверху: он `uint8_t`, и переполнение через 255 сняло бы паузу на
  два круга;
* сравнение таймера через знаковую разность — `no_host_timer > millis()` ломается на
  переполнении `millis()` раз в ~49 суток.

Чинить один способ отказа, оставив рядом два таких же, значит встретить их потом под
другим именем.

**Данные с устройства** после правки:

```
[AUDIO.HLS] playlist has no new segment, empty=2 stalled=0ms     backoff=2000ms
[AUDIO.HLS] playlist has no new segment, empty=4 stalled=4015ms  backoff=2000ms
[AUDIO.HLS] playlist has no new segment, empty=8 stalled=12049ms backoff=2000ms
```

4015 мс на 2 выборки и 8034 мс на 4 — по 2007 и 2008 мс. Частота запросов к CDN упала
с 1,48/с до 0,50/с. Поле `stalled=` добавлено именно ради этого: успех тут выглядит как
**отсутствие** строк, а такое глазами не проверяется — нужно число.

⚠️ Значение 2000 мс не выбиралось, а **сохранено** от прежней одноразовой паузы: если
поведение окажется плохим, будет видно, что виновата частота применения, а не новая
константа.

⚠️ E-HL1 убирает шторм, но не тишину. Если сервер не публикует сегменты, играть нечего;
станция при этом по-прежнему показывает в UI PLAYING. Это отдельная незакрытая задача —
см. «Известные незакрытые дефекты».

---

## E-HL2 — замерший плейлист выглядел как воспроизведение

E-HL1 убрал шторм, но не тишину: если сервер перестаёт публиковать сегменты, устройство
опрашивало плейлист раз в 2 секунды неограниченно долго, а UI всё это время показывал
PLAYING. Тот же исход, который забракован для Ogg-prebuffer в E-FL3, только достигнутый
другой дорогой.

**Правка.** После `M3U8_STALL_GIVEUP_MS` (15 с) простоя сессия перезапускается с
мастер-плейлиста через `connecttohost()`. Бюджет **переиспользуется, а не дублируется**:
перезапуск — одна физическая попытка подключения, то есть ровно одна единица общего
бюджета по контракту `audio_retry_budget.h`. Поэтому вызывается существующий
`attemptInternalReconnect(true)`, а не новый счётчик. Когда бюджет исчерпан —
`finishUnstableStreamExhausted()`, то есть честный STOPPED вместо тишины при PLAYING.

Бюджет возвращается сам: `pollStreamStability()` обнуляет `m_unstableStreamFailures`,
когда поток проиграл достаточно долго. Шесть попыток — это «шесть подряд без признаков
жизни», а не «шесть за всё время».

**Данные с устройства** (окно ещё 30 с):

```
[AUDIO.HLS] playlist stalled 30145ms -> restart session retry=1/6
[AUDIO.HLS] playlist stalled 30163ms -> restart session retry=2/6
[AUDIO.HLS] playlist stalled 30135ms -> restart session retry=3/6
```

Окно выдержано с точностью до 150 мс, бюджет списывается по единице.

### Чего перезапуск НЕ делает — проверено на устройстве

Первоначальное обоснование было **ошибочным**: утверждалось, что перезапуск очистит
память о проигранных сегментах, потому что `setDefaults()` чистит `m_hashQueue`. Лог это
опроверг — после перезапуска снова `5 entries are known and removed`, а не
`all entries are new`.

Память о сегментах HLS живёт в `m_playlistBuff` (URL последнего проигранного сегмента),
и `setDefaults()` её не трогает. **Это правильно и менять не следует:** забыть последний
сегмент значит переиграть те же ~25 секунд заново, то есть выдать слышимый повтор вместо
восстановления. Настоящий HLS-клиент в такой ситуации по стандарту ждёт, а не отматывает
назад.

Перезапуск обновляет TLS-соединение и конечный автомат плейлиста — это лечит залипший
сокет, но **не пустой плейлист**. Станция, чей плейлист отдаёт только известные сегменты,
израсходует бюджет и остановится.

⚠️ Отсюда главное число этого среза: худшая тишина = `M3U8_STALL_GIVEUP_MS` ×
`MAX_UNSTABLE_STREAM_FAILURES`. При 30 с это было ~3 минуты, поэтому окно снижено до
**15 с** (около трёх пропущенных сегментов подряд) — худший случай ~1,5 минуты. Эти две
константы нужно читать вместе: по отдельности ни одна не показывает цену ожидания.

# Намеренно НЕ менялось

Перечислено осознанно — это не забытые места, а принятые решения.

* **`bitReader_adv()` не сделан «залипающим» на конце пакета.** Там условие
  `headend < 1` срабатывает уже на последнем **валидном** чтении, поэтому залипание
  сломало бы нормальное декодирование.
* **Уровни логов выше ERROR не включались.** `-DCORE_DEBUG_LEVEL=0` в `platformio.ini`
  по-прежнему глушит `VORBIS_LOG_WARN/INFO/DEBUG/VERBOSE`. Это осознанный выбор для
  релиза. Уровень **ERROR от него не зависит начиная с E-VS6** — ошибки декодера в
  серийнике видны.
* **Отвергается `-1`, а не «ноль».** `s_nrOfCodebooks` имеет тип `uint8_t`, а Vorbis
  допускает 256 кодбуков, что и так переполняется в 0. Проверка на «ноль» отвергла бы
  валидный поток.
* **Политика проверки сертификатов не менялась** — как был `setInsecure()`, так и остался.
* **`openai_speech()` не трогался** — он использует hostname-форму `connect()`, где SNI и
  так корректен, хотя и в обход собственного resolver'а.
* **`src/src/audioVS1053/` не трогался** — он собирается только при `I2S_DOUT == 255`, для
  этой платы выключен. Те же шаблоны там присутствуют.
* **Кодеки, PCM, VU/PPM, gain/mute, metadata, UTF-8, Latin-1 fallback, ID3** — вне области
  правок. AAC decoder/buffer preservation, dedup, staging, prebuffer и clean fallback
  сохранены.

# Известные незакрытые дефекты

Найдены при разборе, но осознанно оставлены — каждый требует отдельной задачи.

1. **Пакет Vorbis крупнее 16 КиБ отвергается.** E-VS5 закрыл переполнение: обе записи
   в `s_lastSegmentTable` проверяются против общей `VORBIS_LAST_SEGMENT_CAPACITY`,
   поднятой с литерала 4096 до 16 384. Остаточное ограничение в том, что `segmentLength`
   из Ogg lacing теоретически доходит до 65 025, и такой пакет теперь не портит кучу, а
   теряется: страница отвергается, вызывающий делает resync. Худший реальный пакет
   Vorbis около 12 КиБ, поэтому на практике не наблюдалось.
2. **`ps_ptr::alloc()` не умеет сообщать об ошибке** — возвращает `void` и при OOM только
   печатает строку. Любое выделение в декодере непроверяемо по построению.
3. **`Audio::decodeError()` принимает `int8_t`**, поэтому коды вроде
   `OV_EBADHEADER (-133)` обрезаются (в `+123`) и различить их внутри невозможно.
   Именно поэтому E-VS3 сделан через отдельный флаг, а не через код возврата.
4. **Недостижимый лог** в `bitReader_adv()`: `VORBIS_LOG_ERROR("error in bitreader")`
   стоит **после** `return -1`.
5. **`mapping_inverse()` выделяет 4 буфера плюс по одному на канал на каждом аудиопакете**
   (~каждые 20–50 мс) и ни одно выделение не проверяет. Кандидат и на производительность,
   и на надёжность.
6. **`clearGlobalConfigurations()` не сбрасывает `s_nrOfModes`**, хотя освобождает
   `s_mode_param`. Сейчас не стреляет благодаря E-VS2, но пара «счётчик + массив»
   рассогласована.
7. **Голодание входа на потоках под мегабит.** E-FL2 дал потокам в контейнере Ogg
   стартовый запас, и это убрало `slow stream` на старте. Но при устойчивой нехватке
   канала (`streams.norbert.de/zappa.flac`, ~0,9–1,0 Мбит/с) сообщение возвращается уже
   в середине воспроизведения: prebuffer задаёт глубину на старте и не создаёт пропускной
   способности. Симптом воспроизводится и по HTTP, и по HTTPS, и наблюдался до правок
   этого файла. Подозреваемый сосед — загрузка CPU от накопления WebSocket-клиентов.
8. **«Снести до проверки».** `vorbisDecodePage1()` уничтожает рабочие таблицы **до** того,
   как станет известно, разберётся ли новый заголовок. Правильное решение — разбирать в
   staging-набор и подменять только после успеха; тогда неудачный разбор не стоил бы
   вообще ничего.

# Отношение к upstream и Maleksm

Сравнение проводилось с pinned upstream (`ESP32-audioI2S`) и с
`yoradio-(Maleksm)-v0.9.720m(23.06.26)`.

| Место | Этот проект (после правок) | Pinned upstream | Maleksm |
|---|---|---|---|
| `mapping_inverse` без проверки выделений | как было | так же | так же |
| `s_nrOfModes` сбрасывается вместе с массивом | нет | нет | нет |
| page 3 включает аудио после ошибки | **исправлено** | нет | нет |
| resync сбрасывает состояние Vorbis | **исправлено** | нет | нет |
| граница `lastSegmentTable`, continued-путь | **есть (16384)** | отсутствует | отсутствует |
| граница `lastSegmentTable`, обычный путь | **есть (16384)** | отсутствует | отсутствует |
| ёмкость `lastSegmentTable` | **16 КиБ** | 4 КиБ | 4 КиБ |
| ошибки декодера видны при `CORE_DEBUG_LEVEL=0` | **да** | нет | нет |
| владение состоянием | файловые статики, живут между потоками | объект на поток | объект на поток |

**Вывод: все перечисленные дефекты унаследованы, это не регрессия форка, и переход на
upstream их не лечит.** Единственное значимое архитектурное отличие — последняя строка:
upstream и Maleksm пересоздают объект декодера на каждый поток, поэтому пары
«счётчик + массив» переинициализируются вместе. Здесь состояние живёт в файловых
статиках и переживает смену потока.

# Как это проверялось

* Компиляционные проверки по **production**-хелперам (не по копиям алгоритма):
  идентичность endpoint, валидность URL, сохранность `query` и `%xx`, арифметика бюджета.
  Плюс mock-база TLS, доказывающая, что hostname доходит до вызова connect ядра.
  **Это не проверка реального TLS handshake.** Лежат локально в `/test/`, который
  намеренно в `.gitignore`.
* Сборка `pio run -e 4848S040`.
* Устройство 4848S040, станция `http://89.223.45.5:8000/geny-160` (ogg-vorbis):
  воспроизведение / STOP / deep sleep / пробуждение по таймеру.

⚠️ **Исходный аварийный сценарий перемежающийся и в проверочных прогонах не
воспроизвёлся.** Правки сделаны по доказанной цепочке из регистрового дампа, а не по
повторённому сбою. Если авария когда-нибудь вернётся, в логе теперь будет видимая улика —
строка `[AUDIO.RETRY] vorbis setup header unusable -> reopen stream`.
